Overview

What this project is about

The log ingestion engine accepts application logs over HTTP and carries them through a durable pipeline. Every entry is validated on its own, enriched with reception metadata, routed to the destination that owns its service, published to RabbitMQ and stored in a per-destination SQLite database. A log that exhausts its storage retries is never lost silently: it is appended to a dead-letter file that can be replayed into the same databases later.

Every step is observable. A single metrics registry counts accepted logs by level and by service, tracks throughput, queue backlog, rate-limited requests, dead-lettered logs and write failures, and publishes them to the dashboard and the metrics page.

Design decisions

  • A thin dependency surface. The HTTP layer, configuration parsing, JSON handling and file handling all use the standard library; the only third-party Go dependencies are the UUID generator, the AMQP client and the pure-Go SQLite driver.
  • One configuration object. Every component receives the same ApplicationConfiguration, assembled from the configuration file and the process environment. Environment values win over file values and invalid settings fail fast at startup instead of surfacing later as broken behaviour.
  • Backpressure over unbounded buffering. The raw-log channel, the fallback buffer and every destination queue are bounded, so a slow dependency slows ingestion down instead of exhausting memory. The only documented loss point is a sustained broker outage that fills the fallback.
  • A broker outage never blocks ingestion. Publishing uses confirms with a five-second timeout and reconnects with backoff. While the broker is unreachable, logs go to a bounded in-memory fallback that a consumer stores directly, so every accepted log follows exactly one path; broker or fallback, and is never published twice.
  • Per-destination storage. Each destination owns its own SQLite database, so one slow or broken destination cannot stall the others. The batch writer retries with backoff before a log is appended to the shared dead-letter file and replayed later.
  • Per-IP rate limiting. The limiter is in-memory and per client IP. The client address is only taken from X-Forwarded-For when a trusted proxy is configured; otherwise the socket address is used, so the header cannot be spoofed to bypass the limit.
  • One source of truth for counters. All metrics live in a single registry whose updates stay cheap on the ingestion path. The queue backlog is refreshed from the RabbitMQ management API under a timeout and falls back to a local estimate when the API is unreachable.
  • Everything embedded. The pages, stylesheet, scripts, the vendored Chart.js and mermaid libraries and the Space Grotesk font are embedded in the binary and served from the same origin, so the interface works fully offline and never contacts a third-party host.

Architecture

Logs enter through POST /logs, are validated per entry and pushed onto a bounded raw_logs channel. Pipeline workers enrich and route each log before the publisher hands it to RabbitMQ. If publishing fails, the log enters the bounded fallback instead. Consumers acknowledge only after the batch writer stores the log in SQLite, and logs whose retries are exhausted go to the dead-letter file for later replay.
